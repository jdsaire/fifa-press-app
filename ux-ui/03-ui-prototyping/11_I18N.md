## 1. What this file decides, and what it does not

**Decides:** the string inventory and its categories (§2); which strings stay English by product-
name rule versus which translate (§3); the seeded-content problem and its resolution (§4); the
switch mechanism and where it lives, including the reload-versus-no-reload question (§5); locale-
aware formatting for dates, times and pluralized durations (§6); layout and contrast re-
verification for longer ES/PT strings (§7); the trilingual break-check applied to every new 4D
surface (§8).

**Does not decide:** the actual translated string values. This is a **scope and mechanism**
specification, not a translation deliverable — translating ~140 distinct strings (§2.4) into two
languages is implementation work for 4E, not a design decision this dossier is positioned to make
well from source inspection. Where this file gives an example translation, it is illustrative only
and 4E's translated strings are authoritative over any example here.

## 2. String inventory

### 2.1 Method

Every `.razor` file under `Pages/`, `Components/`, and `Layout/` was read in full, plus
`MockAccessDataProvider.cs`'s seed data and `wwwroot/index.html`. Strings are grouped into four
categories because each has a materially different localization mechanism — treating them as one
undifferentiated pile is the single most likely way this feature gets under-scoped.

### 2.2 Category A — static UI strings

Labels, headings, button text, nav items, static prose (the Help page's five lifecycle sections,
the sign-in notice, the landing view). These map directly to a resource key and a lookup, one key
per string, no runtime construction. The largest single source is `Help.razor`, whose full content
inventory (`05_SCREENS.md` §4.1) is static by its own state-matrix requirement — "Populated only,"
must render offline — which is convenient here: static content and resource-keyed translation are
the same shape.

**Approximate count:** ~55 distinct strings across `Pages/Help.razor`, `Layout/NavMenu.razor`,
`Components/EventCard.razor`, `Components/RequestAccessForm.razor`, page headings and button labels
app-wide, plus the new sign-in and landing-view copy `10_AUTH-AND-ONBOARDING.md` §2.3 and §6.2
specify. `[ASSUMPTION]` — an exact count depends on final sign-in/landing copy 4E writes from `10`'s
specification, not yet literal text.

### 2.3 Category B — computed and interpolated strings

Strings built at runtime from a template plus a value, where the template itself needs translation
but the mechanism is more than a lookup:

- **`AccessCard.StatusSentence`** — `"Approved until {date}."` The date format and word order both
  vary by locale; a literal `string.Format` swap keeping English word order would misplace the date
  in Spanish or Portuguese for at least the `Refused`/`Withdrawn` variants, which lead with the
  status word.
- **`StaleIndicator.AgeSentence`** — the hardest string in the app to localize correctly. English
  pluralizes with one rule ("1 minute" vs "N minutes"); Spanish and Portuguese both have their own
  pluralization rules that do not map onto English's singular/plural split by simple substitution.
  The existing switch (`< 2 => "1 minute ago"`, `< 60 => "{n} minutes ago"`) is an English-specific
  pluralization ladder baked into C# control flow, not a template. It needs a pluralization-aware
  formatter per locale, not a translated string per branch.
- **`ChangeRow`'s "Takes effect" / "Took effect" plus a formatted date**, and "Recorded {date}" on
  the superseded block — same interpolation-order risk as `StatusSentence`.
- **`MyAccess.LabelFor`** — `"Match {number} — {fixture label}, {city}"`. The fixture label itself
  (`Fixture.DisplayLabel`, `Fixture.PhaseLabel`) is Category C.

**Mechanism:** composite-format resource strings with named placeholders (`"Aprobado hasta {0}."`
rather than string concatenation), so translated word order is free to differ from English, plus
.NET's built-in pluralization-aware APIs (`PluralizationRuleProvider`-equivalent, or a small
per-locale plural-form table if the runtime's built-in support proves insufficient) for the age
sentence specifically. `[ASSUMPTION]`: the exact API surface is 4E's implementation call; this file
specifies that placeholder-based composite formatting is required and that naive concatenation must
not be extended to any new interpolated string.

### 2.4 Category C — enum-derived and entity-derived labels

Every `switch` expression mapping a C# enum to a display string: `MyAccess.TrackName` (3 branches),
`MyAccess.StatusWord` (4 branches), `Fixture.PhaseLabel` (7 branches, including 12 group letters
that are themselves data, not enum members — "Group A" through "Group L" need the word "Group"
translated, not the letter), `AccessCard.StatusSentence`'s status word portion (4 branches),
`FixtureImporter.ZoneByCity`'s time-zone labels (4 distinct labels, currently English prose like
`"Eastern Time (EDT, UTC-4)"`). Each branch is a Category A string in substance — a fixed lookup,
not computed — but grouped separately because these live in C# switch expressions across five
different files rather than in markup, which changes where the resource lookup gets called from.

**Approximate count:** ~24 distinct labels across the branches above.

### 2.5 Category D — seeded free-text content

The hardest category, addressed in full in §4: the five `Change` records seeded in
`MockAccessDataProvider.SeedChanges` (§4.1 below), each carrying 3–4 free-text fields
(`whatChanged`, `reason`, `nextStep`, and `conditionText`/`decidedBy` where present) authored as
English prose sentences directly in C# string literals — not markup, not a resource file, and not
currently structured for translation at all.

**Approximate count:** 18 free-text fields across 5 `Change` records, plus the `Accreditation`
record's `Outlet` and `ZoneAccess` list (proper nouns and short phrases, lower translation risk)
and, once `10_AUTH-AND-ONBOARDING.md` §3.2's second seeded record lands, a comparable set for
Tomás's own change list.

### 2.6 Total, and what the total is for

**Approximately 140 distinct strings** across the four categories, as of the surfaces v10 shipped
plus what `09` and `10` specify. This number exists to size the work, not to be hit exactly — 4E
should re-count against its own final copy rather than reconcile against this estimate the way the
project's link-integrity counts have had to be re-derived before.

## 3. What stays English — the product-name rule, carried and extended

`02_INFORMATION-ARCHITECTURE.md` §5 already resolved this for **Access Record**: the concept name
stays English as a product term; the section a signed-in holder sees uses *mi acceso* / *meu
acesso*. This file extends the same rule to every product-level name 4D and 4E introduce, so
translators are not left to guess which words are names and which are content:

| Term | Treatment | Basis |
|---|---|---|
| **Access Record** | English, always | Gate 2 §5, unchanged |
| **FIFA Press App** | English, always | `03_UI-DECISIONS.md` §4 — chosen to match the repository's own public name; already established as unchanged across EN/ES/PT |
| **My Access** (nav label / page heading) | **Translates** — *Mi acceso* / *Meu acesso* | This is the section label Gate 2 §5 already assigned a translation to; distinct from the product concept name above |
| **Matches**, **Help**, **Sign in**, **Sign out** | Translate | Ordinary nav labels, not product names |
| Track names (Member Association Quota, Rights Holder, Freelance) | Translate | Descriptive category labels, not branded terms — no prior decision holds them in English and nothing about them resembles a product name |
| Demo credential IDs (`MP-2026-04817`, `RH-2026-00219`) | **Never translate or reformat** | Identifiers, not language content, in any locale |

**The rule, stated generally so it does not need re-deriving per term:** a name that identifies the
*product or the concept itself* stays English. A name that identifies *what a person is looking at
or doing* translates. When a new term shows up in 4E that this table does not cover, that test is
the one to apply, not a fresh judgment call.

## 4. Category D — the seeded content problem, resolved

### 4.1 Why this is the real cost of this feature

A resource-key lookup handles Categories A–C without much difficulty. Category D is different: each
`Change` record's `whatChanged`/`reason`/`nextStep`/`conditionText` is **authored narrative prose
specific to that one record** — "Your member association confirmed its opening quota split, and
your name was on it" is not a template with a variable slot, it is a sentence someone wrote once, in
English, for `ch-001`. There are five such records for Amina today, a comparable set coming for
Tomás per `10_AUTH-AND-ONBOARDING.md` §3.3, and every future seed run adds more.

### 4.2 The resolution: seeded content becomes locale-keyed at authoring time, not translated at render time

Each `Change`'s free-text fields are authored as **three parallel strings per field, chosen at seed
time**, not as one English string run through a translation function at render time. Concretely:
`whatChanged`, `reason`, `nextStep`, `conditionText` each become a small per-locale record (three
strings keyed `en`/`es`/`pt`) rather than a single `string`, and the seed data in
`MockAccessDataProvider.SeedChanges` supplies all three at construction.

**Why this, and not a runtime translation call:** this content is a **simulated data asset**, in
the same standing as `TimeZoneLabel` — mocked, labelled as mocked, authored once, and not something
a live translation service would ever touch even in a real deployment (a real accreditation system
would author these three languages the same way a human writer does today, once, at the source).
Treating it as "content to translate" implies a pipeline this project has no reason to build.
Treating it as "content authored in three languages by whoever writes the seed data" matches what
it actually is.

**Cost, stated plainly:** this means every future `Change` seeded into this app is authored three
times, not once. That is a real and recurring cost, not a one-time setup tax, and 4E's Completion
Report should say so rather than presenting it as solved. `[ASSUMPTION]` that this cost is
acceptable at the current, small seed-data scale (five to ten records); it would not scale to a
real multi-holder dataset, which is exactly why it is fine for a demonstration and would not be the
right architecture for `4C`'s eventual real backend.

### 4.3 What `06_DATA-MODEL.md`'s `Change` entity gains

The entity's shape changes from four `string` fields to four `LocalizedText`-equivalent fields (or
three parallel string properties per field — 4E's implementation choice), each resolved to the
active locale at render time. This is a genuine, if small, entity-model change beyond what
`06_DATA-MODEL.md` specified, and it must be named as such in `12_DECISION-REVERSALS.md` or in
4E's own plan — this file is not the place that formally reverses a frozen data-model section, but
it is the place that first identifies the change is needed, so it should not arrive as a surprise
in 4E's diff.

### 4.4 What does not change

The append-only log, the ordering rule (effective date, newest first), the supersession mechanism,
and the withholding rule are all locale-independent and untouched. A change written in three
languages is still one change; switching locale mid-session must never appear to alter, duplicate,
or reorder the log — it changes which of the three parallel strings each field displays, nothing
about the record's identity or count.

## 5. The switch mechanism

### 5.1 Where it lives

`09_DESIGN-ADDENDUM.md` §5.2 already placed the theme control as a row in the relocated nav list.
The language switch joins it as a **separate row**, not folded into the same control — language and
theme are independent choices along different axes, and a single combined control would force a
person to cycle through six states (three languages × two themes) to reach one. Positioned between
Help and the theme row, so the nav list's final order is: My Access · Matches · Help · Language ·
Theme · (Sign out, once `10` §4.1 lands). `[ASSUMPTION]` for the exact position within that tail
grouping; the constraint that matters is that it sits with theme in the non-destination tail, not
among the three destination rows above it.

**Rendered as a compact three-way control** (EN / ES / PT, or a single button cycling through the
three, matching the theme trigger's own toggle-not-menu pattern) rather than a dropdown — consistent
with `09_DESIGN-ADDENDUM.md` §3's clarity principle, and because three fixed options never need a
picker's affordance.

### 5.2 Persistence, and the reload question — stated as a real technical constraint, not glossed over

`ThemeTrigger`'s existing mechanism (`localStorage` + a `data-theme` attribute the stylesheet reads)
works because CSS custom properties re-resolve live with no reload — the browser repaints the moment
the attribute changes. **Text content does not have that property.** Every rendered string in the
app is already committed to the DOM by the time a locale switch happens; changing the active locale
has to actually re-render every localized string on screen, not just flip an attribute a stylesheet
watches.

Two ways to make that happen, both real options and neither free:

**Option A — full reload after storing the choice.** Store the chosen locale the same way theme is
stored (`localStorage`, mirroring `theme.js`'s `storeTheme`/`getStoredTheme` pattern), then reload
the page. Blazor WebAssembly re-initializes with the stored locale as its active culture and every
component renders its strings correctly from the first paint — no partial-render state to manage.
**Cost:** a visible reload flash on every language change, which is a worse moment than the
instant, flash-free theme toggle sets as the app's own bar.

**Option B — in-session re-render, no reload.** Hold the active locale as app state (comparable to
how `ThemeTrigger`'s `current` field works today, but consumed by every component that renders
localized text, not just one), and every localized string read goes through a lookup keyed on that
state rather than a static resource. Changing the locale triggers Blazor's normal re-render cycle
across the component tree. **Cost:** every component that displays Category A/B/C/D content needs
to actually re-render on locale change — which for a `[CascadingParameter]`-style locale value
flowing down from a root component is the standard Blazor pattern, but it is meaningfully more
implementation surface than Option A, and correctness depends on no component caching a localized
string outside the render cycle (a `private string` field set once in `OnInitialized` rather than
computed in the render method would go stale silently).

**Recommended: Option A**, for the same reason `10_AUTH-AND-ONBOARDING.md` §8 left session
persistence unresolved rather than building it — this is a demonstration, and a working reload
delivers the correct, verifiable result with a fraction of the risk surface. The visible flash is a
real cost but a bounded, honest one; a partially-migrated Option B that misses one cached string is
a worse outcome that looks fine until someone finds the one stale label. **This is 4E's
implementation call to confirm, not this dossier's to mandate irreversibly** — flagged as a strong
recommendation with the reasoning attached, not a locked decision, per `guardrails`-style practice
elsewhere in this project's prompts.

### 5.3 What must not happen regardless of which option 4E picks

The active locale must survive the reload/re-render with the rest of app state intact where that
state is itself persisted — a signed-in session (`10_AUTH-AND-ONBOARDING.md` §2 — explicitly **not**
persisted across refresh) is not restored by a locale-triggered reload either; switching language
while signed in signs the person out, and the language switch's own UI should not surprise anyone
with that. This is a direct consequence of `10`'s own §8 decision, not a new constraint, but it is
easy to miss if the two files are read separately, so it is stated here explicitly.

## 6. Locale-aware formatting

**Dates.** Every `.ToString("d MMMM yyyy")`-style call across `AccessCard`, `ChangeRow`,
`EventCard`, `EventDetails`, `Registration` needs to resolve against the active `CultureInfo`
rather than the invariant/default culture the current calls implicitly use — `"3 July 2026"` versus
*"3 de julio de 2026"* versus *"3 de julho de 2026"* is a culture-formatting call, not a translated
string. **Exception, carried forward unchanged:** `FixtureImporter.ParseDate`'s `InvariantCulture`
parse of the source CSV is not touched by this — that is parsing the *input* file, which stays in
one fixed format regardless of display locale; only *display* formatting becomes locale-aware.

**Times.** Currently rendered as `HH:mm`, locale-invariant 24-hour notation. `[ASSUMPTION]`: kept
as-is across all three locales rather than switching to a 12-hour format for any of them, because
24-hour time is standard in Spanish- and Portuguese-language sports journalism as much as in
English, and match kickoff times specifically benefit from a format that never needs an AM/PM
disambiguation a person reads under time pressure.

**Pluralized durations.** `StaleIndicator.AgeSentence`, per §2.3 — the one place in the app doing
its own hand-rolled pluralization logic. This is where a naive per-branch translation would produce
grammatically wrong output in at least Spanish's plural rules, and needs the resolution named there,
not a fresh one here.

## 7. Layout and contrast re-verification

### 7.1 Why this section exists at all

`09_DESIGN-ADDENDUM.md` §8 already flagged the risk in outline: longer ES/PT strings can break a
layout sized for English, and a disclosure control sized for "Show more" may not fit "Mostrar más
detalles." This section makes that concrete against the actual current markup rather than leaving
it as a general warning.

### 7.2 Specific pinch points, identified from source

- **The relocated nav list (`09` §5.2).** Each row is `height: 3rem` with a single line of text.
  *"Solicitar acceso"* (17 characters) against *"Request access"* (15) is a small delta and likely
  fine; the language-switch row's own label and the sign-out label are the ones to check once
  written, since neither has an English baseline yet to compare against.
- **`AccessCard`'s status sentence.** *"Refused. See the changes below for the reason and what
  remains open."* is already a long sentence in English; its Spanish/Portuguese equivalents will run
  longer, inside a `<p>` with no fixed width today — low risk, but worth a rendered check rather than
  an assumption, since it is the single most important sentence on the app's primary surface.
- **`ChangeRow`'s field labels** ("Why", "What you can do") sit as short standalone `<p>` elements
  above their content, not inline — this shape tolerates length growth well since each label owns
  its own line regardless of length.
- **Button and badge text** — `RequestAccessForm`'s submit button ("Request access" /
  "Sending request…"), `ForeseeableBadge`'s default label ("Not decided yet — depends on a match
  still to be played," already the longest single UI string in the app before translation). The
  badge in particular should be checked first in 4E's implementation, since it is already close to
  wrapping in English on a narrow viewport.

### 7.3 Contrast is unaffected, stated once so it does not need re-checking per string

Every token computed in `09_DESIGN-ADDENDUM.md` §4 is a colour-against-colour ratio, independent of
which language's characters sit on top of it. Nothing in this file reopens or requires re-verifying
any contrast ratio — only layout (wrapping, truncation, row height) is a genuine language-dependent
risk, and it is a rendered-check task for 4E, not a value this dossier can compute from source.

### 7.4 Method for 4E's verification pass

Render each pinch point above in all three languages at the narrowest supported viewport (this
app's one breakpoint, `<641px`, per `03_UI-DECISIONS.md` §5) and confirm no label wraps in a way
that breaks its container, no button text truncates, and the nav row heights stay uniform across all
three languages' longest label. This is a visual check belonging to implementation, not something
this dossier can perform from static source.

## 8. Trilingual break-check — applied to every surface 4D adds

Following Gate 2 §5's method exactly: only labels that genuinely break are listed; everything else
translates without incident and is not enumerated.

| Term/surface | Break | Resolution |
|---|---|---|
| **"Stale" / staleness wording** | Already identified in Gate 2 §5 — no single-word ES/PT equivalent, literal translations read as "spoiled." | Already resolved as an explicit timestamp phrase; `09`/`10` introduce no new instance of the bare word, so this is carried, not reopened |
| **Sign-in "simulation" framing (`10` §2.3)** | Low. *Simulado/a* and *simulação/simulación* both carry the right sense in ES/PT with no false-friend risk | Direct translation; listed only to confirm it was checked, per Gate 2 §5's own listing convention for a confirmed non-break |
| **"Demonstration" on the landing view (`10` §6.2)** | Low. *Demostración*/*demonstração* both work | No action |
| **`ForeseeableBadge`'s "may" / conditional framing** | Moderate. The badge's English wording leans on modal auxiliaries ("may," "depends on") to avoid sounding like a settled decision — Spanish and Portuguese express the same conditionality through different grammatical means (subjunctive mood, or phrasing like *"aún no decidido"*/*"ainda não decidido"* rather than an English-shaped modal). Not a break, but a translation that copies English sentence structure risks losing the deliberate hedging `ForeseeableBadge.razor`'s own comment calls out as load-bearing | 4E's translator must be told explicitly what job this sentence is doing (never sound like a commitment), not just given the English source string to convert word-for-word |
| **Track name "Rights Holder"** | Low structurally, but note for consistency: `05_ARTIFACTS.md` and `10_AUTH-AND-ONBOARDING.md` both use "rights-holder" as a compound descriptor; ES/PT equivalents (*titular de derechos* / *detentor de direitos*) are established sports-broadcasting terminology, not a literal translation risk | No action; noted so a translator does not second-guess an established industry term |

**Nothing else in `09` or `10`'s new content breaks** by this method — the remainder is
straightforward prose translation with no false friends, no missing target-language concept, and no
grammatical structure this table has not already covered.
