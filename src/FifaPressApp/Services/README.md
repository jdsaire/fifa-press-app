# Services/

Holds the app's shared, ongoing memory — plain C# classes that aren't tied to any single screen, created once when the app starts, and shared by whichever pages need them. This is what lets information survive moving from one page to another, which nothing in `Pages/` or `Components/` can do on its own.

## The data layer

- **`IAccessDataProvider.cs`** — the contract every page and component talks to, and the first file in this whole feature that was written. Nothing in the app names a concrete provider, so replacing the in-memory one with something that talks to a real service is a change to one line in `Program.cs` rather than a change to every caller. It also carries four rules so its callers don't have to: every read reports its own freshness, reads come from local state before the network, writes return the change they produced rather than a success flag, and no method hands out the teams for a match that hasn't been played.
- **`MockAccessDataProvider.cs`** — the only implementation this version ships, holding everything in memory — now for two seeded holders, resolved by whichever credential the session holds. It owns a simulated "now", and that's what makes the last rule above enforceable: team names get attached to a match in exactly one method, which refuses to attach them to a match that hasn't kicked off. Every read path goes through it, so a caller can't opt out by forgetting.
- **`FixtureImporter.cs`** — reads the published schedule CSV into fixtures. Kept separate from the provider on purpose: it knows about a file format and nothing about entitlements. Three things in the file are genuinely awkward — a date format that parses differently depending on machine settings, two team names crammed into one column, and three rows whose kickoff time is written `24:00`, which is not a time a clock can show.
- **`FixtureQuery.cs`** — the match list's search and filters, as pure functions over a list of fixtures. Moved out of `Pages/EventList.razor` so the query can be tested without rendering a page. It knows nothing about the withholding rule and needs to know nothing about it: it filters whatever fixtures it is handed, and the provider has already decided which of them may carry a team name. A second `Search` overload additionally matches a fixture's round in the active language — additive only: every input that matched the original overload still matches through this one.
- **`FixtureLabels.cs`** — how a fixture is named on screen, in whichever language the screen is in. Deliberately *not* a property on `Fixture` itself: the model's own `DisplayLabel`/`PhaseLabel` have to stay English, because a frozen test asserts an exact English sentence against them. This is the rendering that sits between that canonical English and what a reader actually sees.

## Identity and language

- **`DemoAccountStore.cs`** — the two published demo accounts and the one credential check this app performs. Explicitly documented as *not* a credential store: the passwords are compiled into the app and printed on the sign-in screen, so there is nothing to protect and nothing to hash.
- **`SimulatedSessionProvider.cs`** — who is signed in, for as long as the browser tab lasts. The `AuthenticationStateProvider`-equivalent this app can actually build: the real one isn't in this project's dependency graph, so this is the same shape under an honest name, with its own remarks stating plainly that it protects nothing.
- **`LocaleService.cs`** — the active language, the three loaded dictionaries of translated strings, and every date this app formats. All three languages load once at startup, so a language switch is a dictionary lookup, not a fetch — nothing to wait for, nothing that can fail halfway. It also owns date formatting itself rather than handing it to .NET's own culture machinery, because the WebAssembly runtime ships a set of language data that depends on which language the app *started* in — an app that opened in English never receives Portuguese's, and a date silently comes out wrong on a switch. Reading month names from this file instead sidesteps that entirely.
- **`ChangeTemplates.cs`** — the sentences this app writes for itself, in all three languages, when a person requests or withdraws access. Distinct from the *interface* strings `LocaleService` reads from JSON: this is record content, authored the same way the seeded changes below are, because a real accreditation system would author it once, at the point a change is written, not translate it afterward.
- **`ChangeArrivalTracker.cs`** — remembers, for exactly one read, which change a person just wrote — because submitting a request navigates to a freshly loaded record screen, and that screen has no other way to tell its own newest row from the ones that were already there.

## Retained from the earlier build

- **`SessionTracker.cs`** — answers "what has this visitor done in this session?"
- **`AttendanceTracker.cs`** — answers "how many people signed up for this?"

Both are kept rather than deleted. The count they backed is no longer displayed anywhere, but removing a display element and deleting the working code behind it are two different decisions, and only the first one has been taken. Neither is used to record access any more: access moves only by writing a change through the provider above, and having a second way to change it would defeat the point of keeping a record at all.

For why keeping the two trackers separate mattered enough to be a deliberate choice, see [`learning-mode/03-Adding-Signups-and-Headcounts.md`](../../../learning-mode/01-architecture-foundation/03-Adding-Signups-and-Headcounts.md#why-keeping-them-separate-was-a-deliberate-choice).
